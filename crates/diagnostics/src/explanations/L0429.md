# L0429 — there is no `Int` for a width to widen to or to narrow from

`Int` compiles to a `long`, and a great many Java members give back an `int` instead.
Which of the two a member gives is written in that member's own class file, and the compiler
reads none, so `int` after the kind is how a declaration says it.

```text
extern method int to_path(file: File) -> Path = "toPath"
```

`toPath` gives back a `Path`, which is a reference and never a number, so there is nothing for
an `int` to widen to.
The answer is to drop the word:

```text
extern method to_path(file: File) -> Path = "toPath"
```

The word is written where the member really does give an `int`, and then the result is the `Int`
it is widened to:

```text
extern method int length(text: String) -> Int = "length"
```

One rule holds for every kind.
A `new` meets it the way any other does, because the class a constructor gives back is not `Int`.
An `Option` and a `Result` around the result are read through, so `Result<Int, String>` written
`int` is accepted and `Result<Path, String>` is not.

`char` is the other width a result writes, and it reads exactly as `int` does:
`extern method char at(text: String, int index: Int) -> Path` is refused for the same reason.

A parameter meets the rule from the other side.
`int` before a parameter's name says the member takes one there, so the argument is narrowed from
the `Int` the parameter declares, and a parameter of any other type has no `Int` to narrow:

```text
extern method sub(text: String, int from: String) -> Option<String> = "substring"
```

The answer there is the same one: drop the word, or take an `Int`.

`int` is no Lumen type and no program can write one.
It is a fact about the member, written where every other fact about the member is written, and
it is an ordinary name everywhere else: `extern static int(text: String) -> Int` still declares a
function named `int`.

`docs/specs/interop.md` states the widening, the narrowing, and what each refuses.
