# L0412 — a parameter is a bare `Bool`

`open(true)` says nothing.

```
fn open(path: String, read_only: Bool) -> File {
```

A reader of the call has to find the declaration to learn what is true.
`open(path, false)` is one keystroke away and does the other thing without looking wrong.
A `Bool` parameter is the `Flag Argument` a linter reports after the fact, and Bux refuses it.

A two-variant type takes its place:

```
type Mode =
    | ReadOnly
    | ReadWrite

fn open(path: String, mode: Mode) -> File {
```

`open(path, ReadOnly)` says which of the two it means, with no declaration to look up.
A third mode is then a variant rather than a second flag.
Every `match` on `Mode` is made to answer for it.

## The one carve-out

A function whose parameters and result are all `Bool` is a boolean operation.
Its parameters are `Bool` because that is what the function is about.

```
fn implies(first: Bool, second: Bool) -> Bool {
    !first || second
}
```

Nothing else is carved out.
`fn spoken(loudly: Bool) -> String` takes a flag however its parameter is named.
What comes back is not a `Bool`, so the `Bool` was a choice rather than an operand.

A record field, a variant payload, a binding, and a result type may each be a `Bool`.
The rule is about what a call passes, which is the one place a bare `true` loses its meaning.
